# K8s 实验手册编辑规范（Style Guide）

> 本规范是拆分后各章节文件（`01` ~ `09`）修改时的统一对照基准。
> 逐章修订时以本文件为准，修订后如发现规范本身不合理，先更新本规范再继续。
> 文件范围：仅针对 `01-cluster-installation.md` ~ `09-performance-and-monitoring.md`，不含 `00-Kubernetes 核心知识.md`（完整版暂不动）。

## 1. 文件与命名

| 规则 | 说明 |
|---|---|
| 文件名保持 `NN-english-name.md` | 全小写英文、单词间用 `-` 连接，不修改现有 01~09 文件名 |
| 目录结构不变 | 全部放在 `02-Kubernetes核心知识/` 下，与 `00` 完整版共存 |

## 2. 章节文件标准结构

### 2.1 章节骨架

每个章节文件统一为以下骨架（`<>` 为占位）：

```markdown
# <章节名称>          ← 一级标题，保持原样

## 实验准备

- 前置条件：<依赖 实验 01 部署的 3 节点集群等>
- 公共基础：<引用 实验 01 「Kubectl 基础与公共操作」>
- 自包含说明：<yaml 已内嵌，无需克隆仓库>

## Lab N <Lab 名称>            ← 每节一个，编号连续

（Lab 内部结构见 §2.2）

## 本章小结          ← 章节末尾必填

<用表格总结各 Lab 验证的知识点 + 核心认知 + 与后续章节的衔接>
```

### 2.2 Lab 内部完整教学结构（强制）

**每个 Lab 必须按以下 6 个环节组织**，缺一不可：

```markdown
## Lab N <Lab 名称>［分级标记］

> **目标**：<本实验做什么操作>                    ← ① 目标
> **验证概念**：<验证什么概念>                     ← ② 验证概念

<步骤说明文字>

```bash
<可执行命令，纯命令不带提示符>
```

<若需 nano 创建配置文件>

> **配置要点**：<逐字段解释 yaml 关键配置的含义与为什么这样写>   ← ③ 配置要点
> （仅当本 Lab 有 nano 创建 yaml 时必填；多对象/复杂 yaml 的每个关键字段都要解释）

<预期输出（若展示）>

> **观察点**：<输出中重点看哪些字段/属性，学员应观察到什么>   ← ④ 观察点
> （所有 get/describe/explain 的输出块必须配观察点；输出要精简，只保留教学相关字段）

**清理**
<每个 Lab 末尾必须给出清理命令>                  ← ⑤ 清理
```

### 2.2.1 实验分级标注体系（v1.1 新增）

> 配合教材课程主线，对实验做分级标注，帮助学员区分"必做主线"与"可选进阶"。

**三个级别**：

| 级别 | 标注 | 含义 | 使用场景 |
|------|------|------|---------|
| **必做** | 不标注 | 课程主线，必须完成 | 对应教材核心机制的实验 |
| **推荐** | `（推荐）` | 建议完成，加深理解 | 教材讲了、与主线强相关的补充 |
| **可选·进阶** | `（可选·进阶）` | 进阶学员选做 | 需装额外组件/环境依赖/超越 CKA 范围 |

**标注位置**（三处一致）：

1. **Lab 标题**：`## Lab N <名称>（推荐）` / `## Lab N <名称>（可选·进阶）`——必做不加后缀
2. **实验准备**：章首加「实验清单与级别」表：

```markdown
| Lab | 主题 | 级别 |
|---|---|---|
| Lab 1 xxx | xxx | 必做 |
| Lab 5 xxx | xxx | 推荐 |
| Lab 8 xxx | xxx | 可选·进阶 |
```

3. **本章小结**表格加「级别」列，与标题标注一致

**原则**：分级只影响"做不做/何时做"，**不影响六要素完整性**（可选 Lab 同样必须六要素齐全）。

### 2.3 教学结构六要素（Lab 层面）

| 要素 | 要求 | 强制程度 |
|---|---|---|
| ① 目标 | 一句话说明"做什么操作" | 强制 |
| ② 验证概念 | 一句话说明"验证什么知识点" | 强制 |
| ③ 配置要点 | nano 创建的 yaml 逐字段解释（关键字段含义、为什么这样写） | 有 nano 时强制 |
| ④ 观察点 | 每个 get/describe/explain 输出块解释"重点看什么"；输出精简 | 强制 |
| ⑤ 清理 | 删除本 Lab 创建的资源 | 强制 |
| ⑥ 小结 | 章节末尾总结（知识点表 + 核心认知 + 衔接） | 章节级强制 |

### 2.4 结构硬性要求

- 一级标题 `#` 全文件仅一个（章节标题），禁止出现第二个一级标题
- 每个 Lab 用 `## Lab N`（或 `## 任务 N`）起头，**编号从 1 连续递增**，禁止跳号、重复
- 每个 Lab 必须完整包含 §2.2 的教学结构六要素
- 清理步骤统一用正文加粗 **清理**（不要用标题）；若无残留资源，可省略并注明"本实验无残留"
- 章节末尾必须有「## 本章小结」：表格总结各 Lab + 核心认知 + 与后续章节衔接
- 全文件末尾（最后一个 Lab 之后）保持与开头一致的空行结尾

## 3. 前置条件（必须新增，或修订已有）

拆分后每个文件都是独立入口，必须让读者知道"我该在什么环境下做这个实验"。

内容要求（按需出现，不存在的项不写）：

1. **集群状态**：明确依赖 实验 01 部署的 **3 节点集群**（默认基线 v1.36，见 §7）
2. **公共基础**：kubectl 体系 / yaml 语法 / 命名空间 / 标签等基础统一引用 实验 01 「Kubectl 基础与公共操作」，**各章不再重复讲解**
3. **自包含**：所有 yaml 已内嵌在各 Lab 中（`nano xxx.yaml` 创建），**禁止依赖外部 git 仓库获取文件**；需下载的官方 manifest（ingress-nginx、metrics-server 等）给出 curl 下载命令

## 6. 代码块规范

### 6.1 语言标注

- 统一小写标准标注：`` ```bash ``、`` ```yaml ``、`` ```shell ``、`` ```text ``、`` ```json ``
- 禁止 `Bash`、`Shell`、`Plaintext`、`YAML` 等非标准/大写标注（逐章修订时统一替换）
- 纯展示性输出（终端结果、文件内容）用 `text`

### 6.2 命令 vs 输出分离

- **可执行命令块**：只放命令本身，**不带** `root@node1:~/xxx# ` 提示符前缀
- **输出展示块**：保留原始终端实录（**决策：保留**，理由见 §6.4），但统一以 `text` 代码块呈现，与可执行命令块分离
- 终端实录块的呈现方式（二选一，逐章统一）：
  - 方式 A（推荐）：实录块开头加注释行说明这是输出示例，如：

    ```text
    # 以下为命令输出示例（实际输出可能因环境不同而有差异）
    ```

  - 方式 B：实录块保持原样（含 `root@node1:~/xxx#` 提示符），放在可执行命令块**之后**，并用 `text` 标注
- 命令块内禁止出现交互式编辑器操作说明与命令混排（如 `nano xxx.yaml` 后直接跟文件内容，需拆成"编辑命令" + "文件内容 text 块"）

### 6.4 关于"保留实录还是文字描述输出"的决策

**结论：保留原始终端实录，不用文字重述"理想输出"。**

理由：

1. **实录是手册的教学核心**。大量实验价值在"真实输出"本身——报错信息（如 `Error from server (Forbidden): pods is forbidden...`）、状态迁移过程（HPA 扩容的 Events 序列）、命令帮助输出，这些是学员对照自己操作结果的关键参照物，文字描述无法替代
2. **避免信息失真**。用文字重写"理想输出"需要人工转译，容易丢失细节或引入与真实环境不符的描述；保留实录即保留原始真实性
3. **成本可控**。实录与可执行命令分离（§6.2）后，复制执行的痛点已解决，无需进一步改写
4. **与 Killercoda 环境兼容**。实录来自同类在线实验环境，学员在 Killercoda 上操作时输出可高度对照

### 6.5 命令行 vs yaml 的使用边界（重构决议）

**结论：简单操作优先命令行，复杂编排用 yaml。**

| 场景 | 方式 | 示例 |
|---|---|---|
| 单容器 + 简单属性（env/args/资源） | `kubectl run --env=... --command ...` | `kubectl run nginx --image=nginx --env=KEY=VAL` |
| 需要 hostPort / 多容器 / 卷 / 探针 / initContainer | yaml | 见 实验 02 Lab 4/5、实验 08 Lab 1 |
| 多对象编排（Deployment/Service/Ingress/PVC） | yaml + `--dry-run=client -o yaml` 生成骨架 | 见 实验 01 公共基础 §3 |

原则：教学上先演示"命令行快"，再演示"yaml 完整"；能用命令行的不写 yaml，但保留 yaml 的等价写法作为对照。

### 6.3 其他

- 命令与说明文字之间保持一个空行
- 长的 YAML 文件内容用独立 yaml 代码块，不从命令块中截断

## 9. 语言与措辞

- 全文中文正文，代码/命令/标识符保持原样
- **AI 生成解释段落的处理**（`>` 引用块中"这是一个……的配置""这些参数是……"这类 AI 逐条解说）——**决策：删除，理由见 §9.1**；如信息对教学必要，压缩为 1~2 句正文说明（不带 `>` 引用）
- 重点清理：`09`（约 75 处）、`01`（2 处）
- **删除对话式残留**：如"与之前提供的配置文件相比""相对于您之前提供的配置文件"这类脱离对话上下文无法理解的句子（重点：`05`、`06`），改为直接描述当前文件内容
- 语气统一为操作手册口吻："执行以下命令""创建该文件"

### 9.1 为什么删除 AI 解释段落

1. **来源不一致**：这些段落是文档处理时 AI 自动生成的解说，非原作者教学正文，与手册语气、详略风格冲突，混排后"谁在说话"不清晰
2. **信息冗余**：绝大多数是对紧邻代码块/命令的逐条复述（如把 YAML 每个字段翻译一遍），读者在看代码本身就能获得，重复占用篇幅、打断实验步骤节奏
3. **脱离对话上下文后语义断裂**：部分段落引用"之前提供的配置文件"等对话语境（05、06），拆分为单文件手册后读者无法理解所指，属于**失效文本**
4. **引用块语义被占用**：Markdown 中 `>` 引用块通常表达"注意/提示"，被大段 AI 解说占用后，真正的注意事项无处安放
5. **保留方式**：确有教学价值的解说（如 09 的 HPA 参数含义）压缩为 1~2 句正文放在对应位置，避免信息完全丢失
