### 维度一：🏗️ 集群规划与容量设计

**现状**：ch03 有 CIDR 三网段规划（极好），ch04 有 QoS 策略，但缺少从"给我一个业务需求"到"设计出一个集群"的完整规划链路。

**建议增补内容**：

#### 1.1 节点规格选型指南（建议加入 ch03）

```
┌─────────────────────────────────────────────────────────────┐
│                    节点规格选型决策树                          │
├─────────────────────────────────────────────────────────────┤
│ 控制面节点：                                                 │
│   · 小型集群（<50 节点）：4C/8G/50G SSD                      │
│   · 中型集群（50-200 节点）：8C/16G/100G SSD                 │
│   · 大型集群（200+ 节点）：16C/32G/200G SSD（etcd 独立部署）  │
│                                                             │
│ Worker 节点：                                                │
│   · 通用型：8C/32G（适合大多数微服务）                        │
│   · 计算密集型：16C/32G（适合 CPU 密集型应用）                │
│   · 内存密集型：8C/64G（适合缓存/JVM 应用）                  │
│   · GPU 节点：按 AI/ML 需求独立规划                          │
│                                                             │
│ 黄金法则：                                                   │
│   · 宁可多节点小规格，不要少节点大规格（爆炸半径更小）         │
│   · 单节点 Pod 密度建议不超过 110（kubelet 默认上限）          │
│   · 预留 kube-reserved + system-reserved ≈ 节点总资源的 15-20%│
└─────────────────────────────────────────────────────────────┘
```

#### 1.2 CIDR 容量推演（建议加入 ch03）

| Pod 网段 | 每节点子网 | 最大节点数 | 最大 Pod 数 |
|----------|-----------|-----------|------------|
| /16 | /24 | 256 | 65,536 |
| /12 | /24 | 4,096 | 1,048,576 |
| /16 | /25 | 512 | 65,536 |

> 设计要点：Service CIDR 通常 /12 即足够（4096 个 Service），但 Pod CIDR 必须根据节点数和每节点最大 Pod 数反推。

#### 1.3 etcd 性能基线（建议加入 ch03 或 ch14）

- etcd 对**磁盘延迟极度敏感**，生产环境**必须使用 SSD**（fsync 延迟 < 10ms）
- 推荐 IOPS ≥ 3000（机械硬盘会导致选举超时和集群不稳定）
- 数据库大小监控：`etcdctl endpoint status` 中的 DB SIZE 超过 2GB 需告警，超过 8GB 需紧急处理
- 定期压缩（compact）+ 碎片整理（defrag）纳入运维日历

#### 1.4 节点系统内核调优基线（建议加入 ch03）

```bash
# 生产节点推荐 sysctl 参数
net.bridge.bridge-nf-call-iptables  = 1
net.ipv4.ip_forward                 = 1
fs.inotify.max_user_watches         = 524288    # 大量 ConfigMap 挂载场景
fs.file-max                         = 1048576   # 高并发连接
net.netfilter.nf_conntrack_max      = 1048576   # Service 多时防 conntrack 表满
net.ipv4.tcp_keepalive_time         = 600       # 长连接优化
vm.max_map_count                    = 262144    # ES 等应用需要
```

### 维度二：🏢 多租户治理体系

**现状**：ch11 提到"按团队/项目拆命名空间"，ch07 有 ResourceQuota/LimitRange，但缺少一个完整的多租户治理框架。

**建议增补内容（建议在 ch07 或 ch14 中新增"多租户治理设计"小节）**：

#### 2.1 命名空间规划模型

```
模型一：按环境划分（适合小团队）
  └── dev / staging / production

模型二：按团队×环境划分（适合中型组织）
  └── team-order-dev / team-order-prod / team-payment-dev / team-payment-prod

模型三：按业务域划分（适合大型组织）
  └── domain-trade / domain-payment / domain-logistics
      每个域内再按微服务部署，跨域通过 NetworkPolicy 隔离
```

#### 2.2 多租户隔离四层模型

| 层级 | 机制 | 隔离强度 | 适用场景 |
|------|------|---------|---------|
| **L1 逻辑隔离** | Namespace + RBAC | ⭐⭐ | 同信任域内团队 |
| **L2 资源隔离** | ResourceQuota + LimitRange | ⭐⭐⭐ | 防 Noisy Neighbor |
| **L3 网络隔离** | NetworkPolicy | ⭐⭐⭐⭐ | 跨团队安全边界 |
| **L4 节点隔离** | Taint/Toleration + 专用节点池 | ⭐⭐⭐⭐⭐ | 合规/安全敏感负载 |

#### 2.3 资源超卖策略

- **测试环境**：超卖比 200-300%（requests 设低，limits 设高，允许争抢）
- **生产环境**：超卖比 120-150%（requests 接近实际用量，limits 设合理上限）
- **核心服务**：超卖比 100%（Guaranteed QoS，requests = limits，零争抢）
- **监控指标**：节点实际利用率 / 节点 requests 总和 = 实际超卖比，超过 85% 触发扩容

### 维度三：🛡️ 高可用与灾备架构设计

**现状**：ch14 有 etcd 备份和控制面 HA，ch06 有 PDB，但缺少从应用视角的端到端高可用设计框架。

**建议增补内容（建议在 ch14 或 ch16 中新增"高可用架构设计"小节）**：

#### 3.1 高可用设计检查清单

```
□ 控制面高可用
  ├── API Server: ≥3 副本 + 前端负载均衡（VIP/SLB）
  ├── etcd: 3/5 节点奇数部署 + SSD + 跨机架/AZ
  └── Scheduler/Controller-Manager: Leader 选举（内置）

□ 应用层高可用
  ├── 副本数: 无状态服务 ≥2 副本（关键服务 ≥3）
  ├── 打散策略: topologySpreadConstraints 跨 AZ 均衡
  ├── PDB: 所有多副本服务必须配置（maxUnavailable: 1）
  ├── 探针: readiness + liveness + startup（慢启动服务）
  └── 优雅终止: preStop + terminationGracePeriodSeconds

□ 数据层高可用
  ├── 有状态服务: StatefulSet + 跨 AZ PV
  ├── 数据库: 主从/集群模式 + 独立备份
  └── 对象存储: 跨区域复制
```

#### 3.2 灾备等级与 RTO/RPO 规划

| 灾备等级 | RTO | RPO | 实现方案 | 成本 |
|---------|-----|-----|---------|------|
| **L1 基础** | < 4h | < 24h | etcd 快照 + 异地存储 | 💰 |
| **L2 标准** | < 1h | < 1h | etcd 快照 + PV 快照 + Velero 定时备份 | 💰💰 |
| **L3 高级** | < 15min | ≈ 0 | 多集群主备 + 数据同步 + DNS 切换 | 💰💰💰 |
| **L4 同城双活** | ≈ 0 | 0 | 跨 AZ 集群 + 全局负载均衡 | 💰💰💰💰 |

#### 3.3 故障域设计原则

```
故障域从小到大：容器 → Pod → 节点 → 机架 → 可用区 → 区域

设计原则：
  · 单个故障域的失败不应导致服务完全不可用
  · 控制面组件至少跨 2 个故障域
  · 核心业务 Pod 至少跨 2 个可用区（topologyKey: topology.kubernetes.io/zone）
  · 数据副本至少存在于 2 个独立故障域
```

### 维度四：🚀 发布与变更管理规范

**现状**：ch05 讲了滚动更新机制，但缺少企业级的发布策略选型和变更管理流程。

**建议增补内容（建议在 ch05 中新增"生产发布策略设计"小节）**：

#### 4.1 发布策略选型矩阵

| 策略 | 原理 | 回滚速度 | 资源开销 | 适用场景 | K8s 实现方式 |
|------|------|---------|---------|---------|-------------|
| **滚动更新** | 逐批替换旧 Pod | 中 | 低（+1 Pod） | 大多数无状态服务 | Deployment 原生 |
| **蓝绿部署** | 新旧两套完整环境切换 | 极快（切 Service） | 高（2x 资源） | 需要瞬间切换 | 两个 Deployment + Service selector 切换 |
| **金丝雀发布** | 小比例流量验证后逐步放大 | 快 | 中 | 高风险变更 | 两个 Deployment + Ingress 权重 / Argo Rollouts |
| **A/B 测试** | 按用户特征分流 | 快 | 中 | 功能验证 | Ingress Header 路由 / Service Mesh |

#### 4.2 变更管理规范

```
变更窗口设计：
  · 常规变更：工作日 10:00-16:00（避开早高峰和下班前）
  · 高风险变更：周二/周三 10:00-14:00（留足观察和回滚时间）
  · 禁止变更：周五下午、节假日前一天、大促期间

变更流程（标准）：
  1. 变更申请 → 2. 同行评审 → 3. 预发环境验证 → 4. 灰度发布（≤10%流量）
  → 5. 观察期（≥15分钟） → 6. 全量发布 → 7. 发布后验证

回滚决策：
  · 错误率上升 > 基线的 2 倍 → 立即回滚
  · P99 延迟上升 > 基线的 3 倍 → 立即回滚
  · 任何数据异常 → 立即回滚并暂停后续发布
```

### 维度五：🏷️ 企业级命名与标签规范

**现状**：ch02 介绍了 Label/Annotation 概念，但全书缺少一套可落地的企业级命名规范。

**建议新增一节（建议加入 ch02 或作为附录）**：

#### 5.1 Kubernetes 推荐标签体系

```yaml
# K8s 官方推荐标签（所有工作负载必须携带）
metadata:
  labels:
    app.kubernetes.io/name: order-service        # 应用名
    app.kubernetes.io/version: "1.2.3"           # 版本号
    app.kubernetes.io/component: api             # 组件角色
    app.kubernetes.io/part-of: e-commerce        # 所属系统
    app.kubernetes.io/managed-by: helm           # 管理工具
  annotations:
    team: trade-team                             # 负责团队（用于告警路由）
    oncall: zhangsan@example.com                 # 值班人员
    cost-center: "BU-001"                        # 成本中心（用于计费）
```

#### 5.2 命名空间命名规范

```
格式：{团队/业务域}-{环境}
示例：
  · order-dev / order-staging / order-prod
  · infra-monitoring / infra-logging
  · shared-middleware

禁止：
  · 使用纯数字或无意义缩写
  · 超过 63 个字符（K8s 限制）
  · 使用下划线（DNS 不兼容）
```

#### 5.3 对象命名规范

| 对象类型 | 命名格式 | 示例 |
|---------|---------|------|
| Deployment | `{app}-{component}` | `order-api`, `order-worker` |
| Service | `{app}-{component}-svc` | `order-api-svc` |
| ConfigMap | `{app}-{用途}-config` | `order-api-env-config` |
| Secret | `{app}-{用途}-secret` | `order-db-credential-secret` |
| Ingress | `{app}-{component}-ingress` | `order-api-ingress` |
| PVC | `{app}-{component}-data` | `mysql-master-data` |
| RBAC Role | `{namespace}-{权限描述}` | `order-dev-readonly` |

### 维度六：📊 SRE 运营规范

**现状**：ch16 有排障纪律和混沌工程引入，但缺少 SRE 体系化的运营管理框架。

**建议增补内容（建议在 ch16 中新增"SRE 运营规范"小节）**：

#### 6.1 SLO/SLA 设计框架

```
SLI（服务级别指标）→ SLO（服务级别目标）→ SLA（服务级别协议）

常见 SLI 指标：
  · 可用性 = 成功请求数 / 总请求数
  · 延迟 = P99 响应时间
  · 吞吐 = 每秒成功处理请求数

SLO 设计建议：
  · 核心交易服务：可用性 ≥ 99.95%，P99 < 500ms
  · 内部工具服务：可用性 ≥ 99.9%，P99 < 2s
  · 批处理任务：成功率 ≥ 99.9%，超时率 < 1%

Error Budget（故障预算）：
  · 99.95% SLO = 每月允许 21.9 分钟不可用
  · 预算耗尽 → 冻结新功能发布，聚焦稳定性
  · 预算充足 → 允许更激进的发布节奏
```

#### 6.2 故障复盘（Post-mortem）规范

```
模板结构：
  1. 事件概要（何时发生、持续多久、影响范围）
  2. 时间线（精确到分钟的事件经过）
  3. 根因分析（5 Whys 或鱼骨图）
  4. 影响评估（受影响用户数、业务损失）
  5. 改进措施（每条必须有 Owner 和 Deadline）
  6. 经验教训（哪些做得好、哪些需要改进）

文化原则：
  · 对事不对人（Blameless）
  · 72 小时内完成初稿
  · 改进措施必须进入迭代排期跟踪
```

#### 6.3 运维日历（建议加入 ch14）

| 频率 | 运维项目 | 执行标准 |
|------|---------|---------|
| **每日** | 监控告警巡检 + Pod 异常状态扫描 | 自动化巡检脚本 |
| **每周** | 资源利用率分析 + 容量趋势评估 | requests vs 实际使用 |
| **每月** | 证书有效期检查 + etcd 碎片整理 | 剩余 < 90天 必须续期 |
| **每季度** | 安全漏洞扫描 + RBAC 权限审计 | Trivy + `kubectl auth can-i` |
| **每半年** | 灾备演练（etcd 恢复 + Velero 恢复） | 必须验证 RTO/RPO 达标 |
| **按需** | K8s 版本升级（不跨大版本） | 先 staging → 再 production |
