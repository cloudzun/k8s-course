2.1
Kubernetes 是什么
▸ 定义与来历：开源版 Borg，CNCF 毕业项目
▸ 它解决什么：承接第 1 章的七大痛点
▸ 核心承诺：声明式、自愈、可移植、可扩展
定义与来历
Kubernetes（K8s）
开源的容器编排平台——自动化容器的部署、扩缩容、调度、网络、存储与自愈
名字与出身
希腊语“舵手”；K8s = K + 8 字母 + s
源自 Google 内部集群系统 Borg——“开源版 Borg”
CNCF 毕业项目
2015 年捐赠 CNCF
2018 年首个毕业项目（Graduated）
事实标准
AWS(EKS) / Azure(AKS) / GCP(GKE)
阿里云(ACK) / 华为云(CCE) 全部托管
它解决什么（承接第 1 章痛点）
单机容器痛点Kubernetes 的机制
容器崩了、机器挂了没人管自愈：控制器自动重建、节点故障驱逐（§2.3、第 5 章）
流量波动需要扩缩容弹性：手动 scale + 自动 HPA（第 7 章）
容器 IP 每次重启都变Service：稳定虚拟 IP + DNS 名（§2.2.4、第 9 章）
多副本流量如何分发负载均衡：Service + kube-proxy（§2.5.2）
“活着”不等于“能用”探针：readiness/liveness 健康检查（第 4 章）
容器删除数据丢失持久化：PV/PVC、StorageClass（第 10 章）
配置和密码散落各处ConfigMap / Secret（第 8 章）
核心承诺（设计宣言）
01
声明式，而非命令式
你描述“最终要什么”，K8s 负责“如何达成并持续维持”
02
自愈
系统永不停止地把自己调和到期望状态——崩溃、驱逐、扩容都自动处理
03
可移植
同样的集群和应用可跑在裸机、虚拟机、任意公有云上
04
可扩展
CRD、Operator、CNI/CSI 插件机制——不只是编排器，更是“可编程的平台底座”
2.2
六个核心概念详解
▸ 集群/节点 · Pod · 工作负载控制器
▸ Service · 命名空间 · 标签选择器
▸ 每个概念讲清原理，不满足于一句话定义
集群与节点
控制面节点（Control Plane）
运行集群的管理组件（§2.4）——相当于“大脑”。

默认不运行业务容器（污点保护，第 6 章）；生产通常部署 2-3 个做高可用。
工作节点（Worker Node）
运行业务容器的机器，数量按需扩展。

每个节点固定三件套：kubelet（节点代理）、kube-proxy（网络转发）、容器运行时（containerd）。
节点通过 kubelet 定期向控制面上报心跳 → 控制面据此判断节点是否健康（Ready）
判断集群规模：kubectl get nodes 显示所有节点及状态——排障第一步（第 16 章）
Pod：最小调度单元
Pod 是 Kubernetes 调度的最小单位——不是容器。一个 Pod 包含一个或多个容器，共享：
01
网络命名空间
共享一个 IP 和端口空间
容器间用 localhost 通信
02
UTS 命名空间
共享主机名
03
共享存储卷
Pod 级卷可被内部所有容器挂载
04
同一生命周期
一起创建、一起销毁
Pod 是“逻辑主机”
生命周期：Pending（已创建未调度）→ Running（运行中）→ Succeeded/Failed → 删除（Terminating）
Pod IP 是临时的（重建即变）——这是 Service 存在的原因；“调度、扩缩、自愈”都发生在 Pod 级别
工作负载控制器（Workload Controllers）
控制器是“管理 Pod 的 Pod”——声明“要这种 Pod、要 N 个、怎么更新”，由控制器维持
Deployment
无状态多副本
滚动更新/回滚/扩缩容
StatefulSet
有状态、有序
稳定标识 + 独立存储
DaemonSet
每节点恰好一个
网络/监控/日志采集
Job
一次性任务
成功（Completed）即结束
CronJob
按 cron 定时触发
如每天凌晨备份
选择口诀：无状态用 Deployment、有状态用 StatefulSet、每节点守护用 DaemonSet、一次性用 Job、定时用 CronJob。
Service：稳定入口
问题：Pod IP 是临时的（重建即变），多副本时“该访问哪个 IP”？
01
创建 Service，声明 selector（选哪些 Pod 作后端）
02
分配稳定虚拟 IP（ClusterIP，如 10.96.x.x）——不会变
03
kube-proxy 写转发规则：ClusterIP 流量 → 随机分发到后端
04
集群 DNS（coredns）把 Service 名解析为 ClusterIP
应用用名字访问，不关心 Pod IP——Pod 会死会变，Service 是稳定的
类型：ClusterIP（集群内）/ NodePort（节点端口）/ LoadBalancer（云负载均衡）/ headless（DNS 直返 Pod IP）
命名空间（Namespace）
资源隔离
资源名在命名空间内唯一
同名不同 ns 互不冲突
权限隔离
RBAC 按命名空间授权
（第 11 章）
配额隔离
每个命名空间可设资源配额
（第 7 章 ResourceQuota）
内置命名空间
default —— 默认；没指定时资源都放这里
kube-system —— 系统组件（apiserver/etcd/coredns 等）
kube-public —— 公开信息（集群内所有用户可读）
注意：命名空间隔离“名字”与“权限”，不隔离网络——跨 ns 的 Pod 默认互通（隔离用 NetworkPolicy，第 9 章）
标签与选择器（Label & Selector）
标签（Label）
附加在对象上的键值对：
app=web env=prod tier=frontend version=v1.2
用途：K8s 的“关联机制”全靠标签——控制器选 Pod、Service 选后端、调度选节点（第 6 章）
选择器（Selector）
等值：kubectl get pods -l app=web（=、!=）
集合：kubectl get pods -l 'app in (web,api)'（in/notin/exists）
Deployment 用它管自己的 Pod；Service 用它选后端
标签 vs 注解：标签是“身份证号”（结构化、可被选择器选中）；注解是“备注栏”（任意文本、不能被选择器选中）
示例：selector.matchLabels.app=web —— Deployment 里匹配它管理的 Pod 模板标签；Service 里决定哪些 Pod 是后端

2.3
命令式 vs 声明式，与控制循环
▸ 两种操作哲学：告诉怎么做 vs 告诉要什么
▸ 期望状态与当前状态
▸ 控制循环：自愈与弹性的根源
命令式 vs 声明式：两种操作哲学
命令式（Imperative）——告诉我怎么做
你一步步下达具体指令，系统只执行、不记忆

例：docker run nginx

特点：直接、快速、适合临时操作；但不记录意图——下次还要重新敲一遍
声明式（Declarative）——告诉我要什么
你提交一份期望状态的描述（YAML），系统自己决定怎么做、并持续维持

例：kubectl apply -f web.yaml（3 副本、nginx:1.27）

特点：意图明确、可版本化、可重复、系统持续保证状态（自愈）
三种具体操作模式（kubectl 层面）
模式方式特点
命令式命令kubectl run / scale / delete最快，但无状态记录
命令式对象kubectl create / replace -f file.yaml把 yaml 当一次性指令，覆盖执行
声明式对象（推荐）kubectl apply -f file.yaml以文件为唯一事实来源，可重复应用、幂等
生产标准是 apply：create 在资源已存在时报错（只能建一次）；apply 幂等更新（可反复执行）
为什么生产用声明式（apply）
01
意图即代码
yaml 文件就是“配置即代码”——进 Git 版本管理、可 review、可回滚
02
幂等
同一份 yaml 反复 apply 结果一致——这是 CI/CD 的基础
03
可自愈
系统记住这份期望状态，任何偏离都被自动修复
04
协作标准
create 只能建一次、apply 可反复执行——生产标准是 apply
一句话：命令式是“手把手教系统做”，声明式是“给系统一张目标图，让它自己达成并守住”
控制循环（Control Loop）
① 观察当前状态
（从 apiserver/etcd 读取）
② 与期望状态对比
③ 执行动作
创建/删除/更新，趋近期望
一致 → 回到观察
→ 有差异 →
执行动作后回到观察（循环永不停止）
控制器内部组成：Informer / Reflector（监听 apiserver 事件）→ WorkQueue（待处理队列）→ Worker（对比 spec 与 status，执行调和）
所有控制器（deployment / replicaset / daemonset / job / namespace…）都是这个模式
循环永不停止：“一致”不是终点而是回到观察；“有差异”才执行动作——这就是自愈与弹性的共同引擎。

01

kubectl apply（期望 replicas=3）
02
Deployment 控制器

03
ReplicaSet 控制器

04

05

2.4
控制面组件详解
▸ kube-apiserver：集群的唯一入口
▸ etcd：集群的状态存储
▸ kube-scheduler：调度器（过滤 + 打分）
▸ kube-controller-manager：控制器集合
kube-apiserver：集群的唯一入口
所有请求（kubectl、各组件、Pod 内服务、控制台）都先到这里——“所有组件不直接互访，只通过 apiserver 交互”（星型拓扑）
① 认证 Authentication —— 你是谁？（X.509 证书 / Token / 用户名密码）
② 授权 Authorization —— 你能干什么？（RBAC 检查）
③ 准入控制 Admission —— 请求合法吗？（插件检查/修改，可拒绝）
④ 持久化 —— 写入 etcd
⑤ 返回结果 + 通知关注者（Watch 机制）
两个关键能力：Watch（监听）机制 = 控制循环的“眼睛”；API 发现（kubectl api-resources / explain）
集中管控 = 一处认证授权、一处审计、一处限流；apiserver 起不来 = 集群完全不可用。
etcd：集群的状态存储
所有对象的状态都存这里
Pod / Service / ConfigMap / Secret 的完整定义——丢了 etcd = 丢了整个集群（CKA 必考）
Raft 共识 + 奇数节点
多节点之间投票保证数据一致；需要奇数个（3/5/7）——Raft 要求多数派（2/3、3/5）才能提交
/registry/pods/default/nginx
/registry/deployments/default/web
/registry/secrets/default/mysql-pass
键值对按路径组织 · 客户端端口 2379 · 节点间 2380 · Secret 默认明文（可配静态加密，实验 09 Lab 9）
etcd 只存集群状态，不存应用数据（应用数据在 PV 里）；etcd 是“集群的记忆”，其他组件都是“读记忆的人”
kube-scheduler：调度器
职责：决定新创建的 Pod 落在哪个节点上——不运行容器，只做“分配决策”
阶段一：过滤（Filtering）
排除不合适的节点：
• 资源够吗（CPU/内存 ≥ requests）
• 满足 nodeSelector / 亲和吗
• 污点能容忍吗
• 端口冲突？磁盘压力？
→ 得到“候选节点集合”
阶段二：打分（Scoring）
在候选中选最优：
• 剩余资源越均衡分越高
• 与同应用 Pod 分散开（反亲和）
• 亲和偏好
→ 得分最高者胜出
排障关联：Pod 一直 Pending，十有八九是调度阶段失败——看 Events 的 FailedScheduling 原因（第 16 章）
kube-controller-manager：控制器集合
每个控制器负责调和一类资源（都是 §2.3 控制循环的实例）：
Deployment 控制器
副本/更新状态
ReplicaSet 控制器
副本数量（创建/删除 Pod）
DaemonSet 控制器
每节点一个副本
Job / CronJob
一次性任务 / 定时触发
Node 控制器
节点健康、驱逐
Namespace 控制器
命名空间删除（先清空）
为什么合并成一个进程？每个控制器逻辑上独立，但打包成一个二进制方便部署与升级（kubeadm 只需管一个 Pod）
cloud-controller-manager（云环境）：对接云厂商 API（负载均衡/路由/云盘）——裸机/教学集群没有它
2.5
数据面组件详解
▸ kubelet：节点上的 Kubernetes 代理
▸ kube-proxy：Service 的交通警察
▸ 容器运行时与 CRI：真正跑容器的引擎
kubelet：节点上的“Kubernetes 代理”
管理该节点所有 Pod 的生命周期，并持续向控制面上报节点状态
01
读取 Pod 定义
apiserver 通知“Pod X 调度到本节点”→ 读取 spec
02
调用容器运行时
通过 CRI：建沙箱（pause）、拉镜像、起容器、挂卷配网
03
持续监控
执行探针（liveness 重启 / readiness 摘流量）、采集资源（cAdvisor）
04
心跳上报
每 10s 上报；超 40s 无心跳 → 控制面判 NotReady
关键点：kubelet 是节点侧唯一与 apiserver 对话的人；节点 Ready 与否取决于 kubelet 心跳；端口 10250；静态 Pod 不经调度器
kube-proxy：Service 的“交通警察”
实现 Service 的负载均衡——把发往 Service 虚拟 IP 的流量转发到后端某个 Pod
1. 应用访问 Service：http://10.96.x.x:80
2. 进入节点内核（iptables 或 IPVS）
3. kube-proxy 提前写好的规则匹配到 Service IP
4. 按规则随机/轮询选择后端 Pod IP（Endpoints 列表）
5. DNAT 改写目标地址 → 转发到 Pod 容器
iptables vs IPVS：iptables 是线性链表 O(n)——Service 越多越慢；IPVS 是哈希表 O(1)——直接查表命中
kube-proxy 只做转发不做服务发现（发现靠 DNS）；规则写进内核，流量不经过 kube-proxy 进程
容器运行时与 CRI
kubelet
唯一指挥者
CRI (gRPC)
→
containerd
容器运行时
沙箱管理
Pod 级 pause 容器
容器管理
create/start/stop
镜像管理
pull/list
监控
stats
pause 容器（沙箱）：每个 Pod 最先创建的“占位容器”，持有 Pod 的网络命名空间等共享资源——Pod 的 IP 属于 pause 容器，删 pause = 整个 Pod 消亡
OCI 标准：镜像格式与运行时行为遵循 OCI——第 1 章的 Docker 镜像能被 containerd 直接使用（Docker 多一层 daemon，containerd 更轻）
第 1 章的容器原理（命名空间/cgroups/镜像分层）就是在这里被“执行”的——kubelet 通过 CRI 驱动 containerd 用内核机制跑起容器
2.6
组件通信全流程
▸ 旅程一：kubectl get pods 读请求
▸ 旅程二：kubectl apply 创建 Deployment
▸ 通信安全：TLS 双向证书与关键端口
旅程一：kubectl get pods 读请求
kubectl
读取 kubeconfig（地址 + 证书）
→
apiserver
HTTPS 请求（客户端证书）→ 认证 → 授权 → 准入
→
etcd
读取 /registry/pods
→
返回
apiserver 组装响应 → kubectl 展示
读请求短：kubectl → apiserver → etcd → 回来；kubectl 通常走 apiserver 缓存（watch 已同步），不每次都打 etcd
注意：kubectl 连接用 kubeconfig 里的客户端证书（kubernetes-admin）——没有证书的请求在认证阶段就被拒绝
旅程二：kubectl apply 创建 Deployment
1. 用户 kubectl apply -f web.yaml（发送期望状态）
2. apiserver：认证 → 授权 → 准入 → 写入 etcd
3. Deployment 控制器：Watch 到新 Deployment → 创建 ReplicaSet
4. ReplicaSet 控制器：创建 3 个 Pod
5. Scheduler：绑定 Pod → node2（写入 nodeName 字段）
6. kubelet：Watch 到 Pod 已调度给我 → CRI 拉镜像、建沙箱、起容器
7. kubelet 上报 Running + IP → apiserver 更新 etcd
每一步都是“写对象 → Watch 通知 → 下一个组件处理”的接力；没有任何两个组件直连——这就是声明式。
通信安全：TLS 双向证书与端口
双向 TLS（mTLS）：通信双方都持有证书，互相验证身份——集群有一个 CA，每个组件有自己的证书（由 CA 签发）

对象模型详解
▸ Group / Version / Kind：如何定位一个资源
▸ metadata：对象的身份
▸ spec vs status：期望 vs 当前
▸ 完整示例：Deployment 对象逐字段
Group / Version / Kind：如何定位一个资源
apiVersion: apps/v1 # 组/版本：apps 组的 v1
kind: Deployment # 类型：Deployment
---
apiVersion: v1 # 核心组没有组名
kind: Pod # 只写版本
Group（API 组）：资源的分类。核心组（core）最特殊——没有组名，如 Pod / Service / ConfigMap

其他组：apps（Deployment/STS/DS）、batch（Job/CronJob）、networking.k8s.io（Ingress/NP）、rbac.authorization.k8s.io（Role）
Version：v1（稳定，生产可用）/ beta（测试）/ alpha（实验）
查看方式：kubectl api-resources（列出所有资源）/ kubectl explain pod（写 yaml 的字典）
对象的身份与期望
metadata：对象的“身份”
name —— 命名空间内唯一（DNS 规范）
namespace —— 所属命名空间
labels —— 可被选择器选中
annotations —— 非结构化元数据
uid —— 系统分配、不可变
resourceVersion —— 乐观锁版本号
spec vs status
spec —— 用户编写：描述期望状态（要什么）
status —— 系统维护：描述当前状态（实际怎样），用户不写它

控制器对比两者来调和（§2.3）
记忆：spec 是“心愿单”，status 是“体检报告”
kubectl get pod nginx -o yaml → 上半部分 spec（你写的期望）、下半部分 status（系统填的实际）
“一切皆对象”——理解对象结构就是理解 Kubernetes 的“语法”
完整示例：Deployment 对象逐字段
apiVersion: apps/v1 # 定位：apps 组的 v1 版本
kind: Deployment # 类型：Deployment
metadata: # 身份
name: web # 名称（default ns 内唯一）
namespace: default # 命名空间
labels: # 本对象自己的标签
app: web
spec: # 期望状态（用户写）
replicas: 3 # 期望副本数 → 控制循环维护
selector: # 选择器：管哪些 Pod
matchLabels:
app: web
template: # Pod 模板：描述“要的 Pod 长什么样”
metadata:
labels:
app: web # Pod 标签（必须匹配 selector）
spec:
containers:
- name: nginx
image: nginx:1.27 # 镜像
ports:
- containerPort: 80
# status 由系统填：availableReplicas、conditions 等
这四层结构（apiVersion / kind / metadata / spec）是所有对象的统一骨架——学会看一个，就会看所有

kubectl 与 kubeconfig
▸ kubectl 命令体系：动词 + 资源 + 选项
▸ kubeconfig 三段结构：集群 / 用户 / 上下文
kubectl 命令体系
统一格式：kubectl <动词> <资源类型> [名称] [选项]
动词作用
get查看资源列表（-o wide 更多列、-o yaml 完整对象）
describe查看详细状态 + 事件（排障首选）
apply声明式创建/更新（幂等）——生产标准
run / create / delete命令式快速操作 / 命令式对象创建 / 删除
explain查看字段结构（写 yaml 的字典）
logs / exec / scale日志 / 进入容器（v1.36 需 -- 分隔）/ 扩缩容
config管理 kubeconfig / 上下文
常用选项：-n <ns> 指定命名空间 · -A 所有命名空间 · -l 标签筛选 · -f 从文件 · -w 持续监听
kubeconfig 与上下文
clusters: # 集群：连哪个 apiserver（地址 + CA 证书）
- cluster:
server: https://192.168.0.114:6443
certificate-authority-data: <CA base64>
name: kubernetes
users: # 用户：用什么身份（客户端证书 / token）
- name: kubernetes-admin
user:
client-certificate-data: <证书 base64>
client-key-data: <私钥 base64>
contexts: # 上下文：集群 + 用户 + 命名空间的组合
- context:
cluster: kubernetes
user: kubernetes-admin
namespace: default
name: kubernetes-admin@kubernetes
current-context: kubernetes-admin@kubernetes
多集群 / 多身份切换（CKA 高频）：
kubectl config get-contexts
# 查看所有上下文（* 标记当前）
kubectl config use-context <名>
# 切换上下文
kubectl config current-context
# 看当前上下文
生产上可能有“开发/生产集群、只读/管理员账号”——靠上下文切换，而不是反复改文件
