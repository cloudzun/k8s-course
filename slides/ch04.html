4.1
Pod 的本质：最小调度单元
▸ 逻辑主机：紧密耦合的进程必须同机共存
▸ 共享边界：网络 / UTS / 存储卷 / 生命周期
▸ 单容器 vs 多容器：sidecar / 适配器 / 大使
Pod 是“逻辑主机”：共享什么、为什么共享
设计动机：为什么必须“同机共存”
▸ 主应用 + 日志采集器：同机才能读日志文件
▸ Web 服务 + 本地代理（Envoy）：同机才能拦截流量
▸ 应用 + 配置刷新器：定期拉配置写入共享目录
拆成独立 Pod 的代价
IP 不同（无法 localhost）· 存储不共享 · 生命周期不同步——调度器把整个 Pod 当作整体调度到同一节点
Pod 内共享什么
共享项含义
网络命名空间一个 Pod IP + 端口空间，容器间用 localhost 互访
UTS 命名空间共享主机名
存储卷Pod 级卷可被所有容器挂载（如共享日志目录）
生命周期一起调度、一起终止
不共享：PID 命名空间（默认）、cgroups（各自独立资源限制）
Pod 的 IP 属于 pause 沙箱——“删 Pod = 整个 Pod 消亡”的技术根源
单容器 vs 多容器：三种协作模式
sidecar（边车）
辅助主容器，增强而不侵入
日志采集 filebeat · 指标暴露 exporter · 本地文件同步
Adapter（适配器）
把主容器的输出转换成统一格式
应用日志转标准 JSON · 指标转监控系统格式
Ambassador（大使）
代表主容器访问外部
数据库连接池代理 · 访问外部服务的本地代理
决策逻辑：先问“能不能一个容器搞定？”——单容器最简单、运维成本最低；只有进程必须同生命周期、共享本地资源时才拆多容器（sidecar 等模式）

4.2
容器的配置要素
▸ 镜像与拉取策略：默认策略由 tag 决定
▸ command / args 覆盖 ENTRYPOINT / CMD
▸ 环境变量、标签注解、SecurityContext 安全基线
镜像与拉取策略（imagePullPolicy）
IfNotPresent
本地有就用本地，没有才拉
版本化镜像（nginx:1.27）的默认策略
Always
每次到仓库拉取，检查 digest 有变化就更新
:latest 或无 tag 的默认策略
Never
只用本地镜像，绝不拉取
离线环境、测试镜像
关键认知：默认策略由镜像 tag 决定
带具体版本（nginx:1.27）→ 默认 IfNotPresent（版本不可变，本地有就不重复拉）
用 :latest 或没写 tag → 默认 Always（latest 是“移动靶”，每次启动确认最新）
“tag 即契约”：版本化镜像假设不可变、latest 假设始终要最新——生产永远用具体版本号 + IfNotPresent，规避 :latest 的不可预测性。
（实验 02 Lab 4：拉取策略）
命令与参数：command / args
镜像默认命令来自 Dockerfile（ENTRYPOINT + CMD），Kubernetes 可以覆盖：
K8s 字段覆盖 Dockerfile作用
commandENTRYPOINT替换启动程序
argsCMD替换启动参数
覆盖规则（容易混淆，重点记忆）
01
只写 args → 程序不变（用镜像 ENTRYPOINT），只换参数
02
只写 command → 程序换掉，参数用镜像默认 CMD（必要时同时清掉 args）
03
command + args 都写 → 程序和参数全换
为什么需要覆盖：同一镜像跑不同任务（busybox 既当“睡眠容器”又当“一次性任务”）、调试进 shell、镜像默认命令在集群环境不适用。kubectl 命令式创建用 --command -- <命令>（v1.36 必须带分隔符）
环境变量与标签注解（Pod 层面）
环境变量：传配置最直接的方式
静态值：env: [{ name: MODE, value: prod }]——写死在 Pod 定义里
动态来源：从 ConfigMap / Secret 引用（第 8 章）；从 Downward API 注入自身元数据（§4.5.4）
局限：不适合传“文件型配置”（如整个配置文件）——文件型用 ConfigMap 卷挂载（第 8 章）
标签与注解的区别（Pod 层面补充）
标签 = “被管理的凭据”：Deployment / Service 靠它选中 Pod——标签与选择器必须精确匹配，错了 Pod 就“没人管”（删了不重建、流量不进）
注解 = 声明“意图”：如 kubernetes.io/change-cause（记录更新原因）、监控告警配置——控制器 / 工具读取，但不参与选择
（实验 02 Lab 5 / Lab 7：环境变量、标签与注解）
生产基线：SecurityContext 安全设置区
容器默认以 root 运行（与宿主机共享内核权限，被攻破有逃逸风险）——用 SecurityContext 声明降权与加固：
spec:
securityContext: # Pod 级：对所有容器生效
runAsNonRoot: true # 禁止 root（UID 0），否则拒绝启动
runAsUser: 1000 # 指定运行用户（UID）
containers:
- name: app
securityContext: # 容器级：只对本容器生效
readOnlyRootFilesystem: true # 根文件系统只读
capabilities:
drop: ["ALL"] # 丢弃全部 Linux 能力
字段防什么
runAsNonRoot容器逃逸、root 权限滥用
readOnlyRootFilesystem恶意文件写入（卷仍可写）
capabilities.drop ALL危险内核能力（SYS_ADMIN 等）
allowPrivilegeEscalation: false禁止子进程提权
先建立基线：容器默认不安全 → 用 SecurityContext 显式降权；第 12 章讲 PSA 如何强制它（“自觉 vs 强制”）
4.3
Init 容器：先决条件执行器
▸ 为什么需要：等待依赖、预置数据、预热缓存
▸ 工作机制：顺序执行 · 失败从头重跑 · 共享卷
▸ vs sidecar：“做完就撤”还是“长期伴随”
Init 容器：启动前的“先决条件执行器”
为什么需要 Init 容器
▸ 等待依赖就绪：while ! nc -z mysql 3306; do sleep 1; done
▸ 预置数据 / 权限：下载配置、初始化目录、设置文件权限
▸ 预热缓存：启动前先把缓存填充好
放进主容器的代价：与主进程争抢资源、逻辑混杂、“启动慢被探针误杀”（§4.4.2）
工作机制：主容器之前，做完就退出
01
Init 容器按声明顺序逐个执行（init-1 等待数据库 → init-2 预置数据 → 主容器）
02
某个失败 → 整个 Pod 按重启策略重启，所有 Init 从头再跑
03
与主容器共享 Pod 卷：预置的数据主容器直接读
04
独立镜像：主容器用精简运行时，Init 用带工具的镜像下载数据
“失败从头跑”：Init 可能修改共享卷的中间状态——从第一个重跑保证准备动作的确定性
（实验 02 Lab 3：Init 容器）
Init 容器 vs sidecar 容器
维度Init 容器sidecar 容器
运行时机主容器之前，跑完即退出与主容器并行，长期运行
生命周期一次性与 Pod 同生共死
典型场景等待依赖、预置数据、预热缓存日志采集、本地代理、指标暴露
判断口诀：“做完就撤”用 Init 容器，“长期伴随”用 sidecar 容器
（实验 02 Lab 2 多容器 / Lab 3 Init：对照验证两种容器的运行时机差异）
4.4
容器生命周期管理
▸ 三种状态与退出码：137 = OOM 强杀
▸ 三种探针：readiness / liveness / startup
▸ 探测方式：httpGet / tcpSocket / exec / grpc
▸ 生命周期钩子与优雅终止流程
容器状态、退出码与重启策略
Waiting
正在准备：拉镜像、创建等
Running
正在运行
Terminated
已退出：正常 / 异常，含退出码
退出码排障必读：0 = 正常退出；非 0 = 异常（1 通用错误）；137 = SIGKILL（先怀疑内存超限 OOM）；143 = SIGTERM
restartPolicy：容器失败 / 退出后要不要重启（Pod 级配置）
策略行为适用
Always（默认）任何退出都重启Deployment 等长期服务
OnFailure只有异常退出（非 0）才重启Job 等任务
Never绝不重启一次性批处理任务
三种探针：各管一件事
readinessProbe
就绪探针“能用了吗？”
决定是否把流量发给这个 Pod（Service 后端列表是否包含它）
失败 → 从 Service 摘除（Pod 不重启）
场景：启动慢、要加载缓存 / 连数据库
livenessProbe
存活探针“还活着吗？”
决定是否重启这个容器（自愈机制）
失败 → kubelet 杀容器并按重启策略重建
场景：进程活着但业务卡死（死锁 / 泄漏）
startupProbe
启动探针“开始检查了吗？”
决定 liveness / readiness 什么时候开始检查
启动阶段只查它 → 解决慢启动被误杀
场景：JVM 启动、加载大模型、冷启动慢
最小化原则：只配必要的——readiness 大多数有流量的服务要配；liveness 有死锁 / 泄漏风险时配；startup 启动超过默认 10s 必须配（防被 liveness 误杀）。
（实验 02 Lab 8：readiness 摘流量、liveness 重启，亲眼验证探针行为）
三探针的配合关系与参数速查
容器启动
→
startupProbe
通过？
否 → 继续等待
不查其他探针
→
readinessProbe
通过？
否 → 从 Service 摘除
流量不进入
→
livenessProbe
持续检查
失败 → 重启容器
回到起点（自愈）
readiness 通过后才接流量；liveness 失败 → 重启 → 回到 startup 重新走流程（循环）
探针参数（速查）
initialDelaySeconds 启动后等多久才第一次查 · periodSeconds 探测间隔 · timeoutSeconds 单次超时
failureThreshold 连续几次失败才判定失败 · successThreshold 连续几次成功才判定成功
读图要点：startup 通过前另外两个探针都不查（慢启动保护）；readiness 失败只摘流量；liveness 失败才重启——三个探针的失败后果各不相同
探针的实现方式：怎么探测
方式原理适用
httpGet发 HTTP GET，状态码 200-399 视为成功HTTP 服务（最常用）
tcpSocket尝试建立 TCP 连接，能连上即成功非 HTTP 协议（数据库、Redis）
exec容器内执行命令，exit 0 视为成功无法用端口判断（检查内部状态文件）
grpcgRPC 健康检查协议（v1.24+）gRPC 微服务，无需额外探针实现
选择逻辑：HTTP 服务用 httpGet（最贴近真实可用性）；TCP 服务用 tcpSocket；都没有的用 exec；gRPC 服务用 grpc 探针（要求服务端实现 gRPC 健康检查协议）
注意：探测路径要选“真实反映可用性”的端点（如 /healthz），而不是只返回 200 的静态页
生命周期钩子与优雅终止
postStart（启动后钩子）
注册到注册中心、初始化脚本——与主进程并发执行（不阻塞）；失败不会导致重启（只记录事件）
preStop（终止前钩子）
通知注册中心下线、排空连接、保存状态——阻塞式：必须执行完（或超时）才继续终止流程

优雅终止 = 不丢请求：先摘流量 → preStop 排空存量 → SIGTERM 优雅退出 → 超时才 SIGKILL 兜底——发布、扩缩容、drain 都走这套流程。
4.5
资源模型：requests 与 limits
▸ requests 管调度承诺，limits 管运行上限
▸ CPU 可压缩（节流）vs 内存不可压缩（OOM）
▸ QoS 三档：Guaranteed / Burstable / BestEffort
▸ Downward API：注入 Pod 自身元数据
requests 与 limits：两个不同的机制
requests（请求量）— 调度承诺
告诉调度器“这个容器至少需要多少”——决定 Pod 落在哪个节点（scheduler 过滤依据）
limits（上限）— 运行时限制
告诉 kubelet“最多能用多少”——决定容器能跑多快 / 会不会被杀（运行时执行）
requests: CPU 0.5 / 内存 256Mi ← 调度器：找剩余资源 ≥ 这个值的节点
limits: CPU 1 / 内存 512Mi ← kubelet：容器最多用这么多
CPU 可压缩 → 超限节流（throttling）跑慢点不致命　|　内存不可压缩 → 超限 OOM 被杀（SIGKILL，退出码 137）
生产底线：内存 limits 必须设——防泄漏容器拖垮整台节点（影响同节点其他 Pod）；CPU limit 可选，只是不节流。
（实验 02 Lab 10：requests / limits 生效、超限节流与 OOM）
不设置会怎样？与 QoS 等级
不设置的三种情况
▸ 只有 requests 没 limits：调度有保障，运行时不受限（可超用节点资源）
▸ 只有 limits 没 requests：limits 隐式等于 requests（K8s 自动补）
▸ 都没有：调度“任何节点都行”（可能挤爆别人），运行时无上限（风险）
QoS 等级：决定节点紧张时谁先被杀
Guaranteed（保证）
requests = limits（都设且相等）——最后被杀
Burstable（可突发）
requests < limits 或只设 requests——有保障可超用，中间
BestEffort（尽力而为）
什么都没设——最容易被杀
生产实践：核心服务配 Guaranteed（requests = limits）；一般服务 Burstable；BestEffort 只给测试任务。
（实验 02 Lab 10：requests / limits 生效，超限节流与 OOM）
Downward API：Pod 怎么“认识自己”
解决什么问题
容器内部怎么知道自己的 Pod 名、命名空间、IP、所在节点？——Downward API 把 Pod 自身的元数据注入容器（环境变量或文件两种方式）
两种注入方式
环境变量：Pod 名、命名空间、节点名、Pod IP（label / annotation 不能进 env）
文件方式（volume）：label / annotation 等全部字段，挂载成文件、支持热更新
env:
- name: MY_POD_NAME
valueFrom:
fieldRef:
fieldPath: metadata.name
注入的是“自身信息”，不是外部配置——外部配置用 ConfigMap（第 8 章）
典型用途：应用上报日志时带“我是哪个 Pod”、监控系统标记来源、按 Pod 标签决定行为
走查：一个 Pod 的完整生命周期
01
提交：kubectl apply deployment.yaml（1 副本，带 readiness + liveness 探针）
02
调度：scheduler 按 requests 过滤打分，选中 node2
03
创建：kubelet 建 pause 沙箱 → 拉镜像 → 建容器（Waiting: Pulling）
04
启动：容器 Running；postStart 钩子并发执行（注册 / 初始化）
05
探针：startup 成功 → readiness 成功 → 加入 Service 接流量（liveness 失败即重启）
06
更新 / 删除：摘流量 → preStop 排空 → SIGTERM → 优雅退出（超时 SIGKILL）
07
回收：删除 Pod 对象（中途内存超限可能已 OOM 被杀，退出码 137）
对照第 2 章控制循环：Pod 的生死由 ReplicaSet 控制器监视——它死了，控制器立刻补一个新的（自愈）
