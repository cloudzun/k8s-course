8.1
为什么需要“配置外部化”
▸ 三个痛点：镜像不可变被破坏、多环境无法复用、敏感信息暴露
▸ 十二要素（12-Factor）核心：配置与代码分离——同一份镜像跑所有环境
▸ K8s 的答案：ConfigMap（非敏感）+ Secret（敏感），机制几乎一样
▸ 承上启下：第 4 章 env/command 硬编码 → 本章把配置“抽”出来统一管理
为什么需要“配置外部化”
第 4 章的 env / command 把配置写死在容器里——本章把配置从镜像 / yaml 中“抽”出来统一管理
① 镜像不可变被破坏
镜像一旦构建就不该改；改配置就得重新构建镜像、重新发布
② 多环境无法复用
dev / test / prod 的数据库地址、日志级别不同；写死一份只能服务一个环境
③ 敏感信息暴露
密码写进 yaml → 进 Git → 泄密；写进镜像 → 所有拉取镜像的人都能看到
K8s 的答案：两个专用对象（机制几乎一样，唯一的本质区别是数据的敏感程度）
ConfigMap
非敏感配置：连接串、开关、日志级别
Secret
敏感配置：密码、Token、证书
十二要素（12-Factor）核心：配置与代码分离——同一份镜像，通过注入不同的配置运行在不同环境
8.2
ConfigMap：非敏感配置
▸ 本质：一个“键值对仓库”（data 区）——键可以是短值，也可以是整个文件
▸ 两种消费：卷挂载（键变文件）vs 环境变量注入（键变变量）
▸ 核心差异：卷挂载支持热更新，env 注入需要重启 Pod
▸ 经典陷阱：subPath 单文件挂载丧失热更新；immutable 与 Reloader 是生产方案
ConfigMap 的本质与创建
apiVersion: v1
kind: ConfigMap
metadata:
name: app-config
data:
LOG_LEVEL: info # 键值对（短配置）
APP_PORT: "8080"
app.conf: | # 键=文件名（长配置）
server.port=8080
server.timeout=30
本质：键值对仓库
▸ data 区 = 键值对集合
▸ 短配置：键 = 开关 / 参数，值 = 字符串
▸ 长配置：键 = 文件名，值 = 整个文件内容
▸ 一个 CM 可同时装两类配置
▸ 非敏感：连接串、开关、日志级别
创建方式（实验 06 Lab 1 / Lab 2）
kubectl create configmap app-config --from-literal=LOG_LEVEL=info
kubectl create configmap app-config --from-file=app.conf
kubectl create configmap app-config --from-file=conf.d/ # 目录：每文件一个键
kubectl apply -f configmap.yaml # 声明式（生产推荐）
两种消费方式：卷挂载 vs env 注入
① 卷挂载：键变文件
spec:
containers:
- name: app
volumeMounts:
- name: config
mountPath: /etc/app
volumes:
- name: config
configMap:
name: app-config
挂载后每个键变成一个文件：/etc/app/ 下有 LOG_LEVEL、APP_PORT、app.conf——适合“读配置文件”的应用
② env 注入：键变变量
spec:
containers:
- name: app
env:
- name: LOG_LEVEL
valueFrom:
configMapKeyRef:
name: app-config
key: LOG_LEVEL
只把指定的键注入为环境变量——适合“读环境变量”的应用（12-Factor 风格）
共同点：数据都来自同一个 ConfigMap；区别只在“形态”——文件还是环境变量
读图要点：判断依据是“形态 + 读取方式”——配置文件 → 卷挂载；少量键值且应用读 env → env 注入
两种方式对比与热更新原理
维度卷挂载env 注入
形态键 → 文件键 → 环境变量
应用读取读文件（配置类应用）读环境变量
热更新改 CM 后文件自动更新，无需重启改后需重启 Pod 才生效
场景配置文件、整个 conf 目录少量开关、连接参数
热更新的底层原理（重要）
卷挂载 → 为什么能热更新
kubelet 定期把 ConfigMap 同步到本地缓存目录，挂载是“软链 / 绑定挂载”——CM 变了，文件内容跟着变（应用是否重读文件取决于实现）
env → 为什么不能
环境变量是“进程启动时”注入的——进程已经跑起来，改 env 进不到正在运行的进程，只能重启 Pod（新 Pod 用新值）
决策逻辑：需要频繁改配置、应用读文件 → 卷挂载（热更新）；少量一次性参数、应用读 env → env 注入。
subPath 陷阱与生产性能方案
subPath 挂载陷阱（经典坑，必读）
只挂 ConfigMap 里的单个文件：
volumeMounts:
- name: config
mountPath: /etc/nginx/nginx.conf
subPath: nginx.conf
subPath 是“直接复制文件”（不做软链接）——ConfigMap 更新后文件不会跟着变，彻底丧失热更新，只能重启 Pod
决策：适合“只挂单文件 + 配置基本不变”；要热更新别用 subPath（挂整个目录）
immutable：不可变（省轮询）
immutable: true 后禁止修改（只能删了重建）；kubelet 不再轮询检查变化 → 大规模集群控制面压力大幅下降；适合公共证书、系统级配置等“基本不变”的配置
Reloader：热更新自动化（第三方）
自动监听 ConfigMap / Secret 变化 → 滚动重启关联 Deployment，解决 env / subPath 不能热更新的自动化问题
注解标记：reloader.stakater.com/auto: "true"
生产组合：配置文件卷挂载（热更新）+ 少量参数 immutable（省轮询）+ 需要重启生效的场景用 Reloader 自动滚动。
8.3
Secret：敏感配置
▸ 结构与 ConfigMap 几乎一样，差别在：base64 编码、默认不显示内容、有类型字段
▸ 重要认知：base64 是编码不是加密——安全靠 RBAC + etcd 加密 + 最小权限
▸ 四种类型：Opaque / tls / dockerconfigjson / service-account-token
▸ 两个系统级消费特例：Ingress TLS 与 imagePullSecrets
Secret 与 ConfigMap 的关系
apiVersion: v1
kind: Secret
metadata:
name: mysql-pass
type: Opaque
data:
password: d29yZHByZXNzMTIz
# 值必须 base64 编码（"wordpress123"）
与 ConfigMap 的差别
▸ 值必须 base64 编码（CM 是明文）
▸ describe / get 默认不显示内容
▸ 有 type 类型字段（§8.3.3）
▸ RBAC 可单独收紧授权
▸ 消费方式相同：secret 卷 / secretKeyRef，挂载后自动还原明文
kubectl get secret mysql-pass -o yaml → 密文直接可读、秒还原（实验 06 Lab 4 亲手验证）
base64 只是“字节 → 可打印字符”的编码，任何人都能解码——“传输 / 存储格式”不等于安全
base64 是编码不是加密：任何人拿到 yaml 都能秒解码——Secret 的真正安全依赖 RBAC + etcd 静态加密 + 最小权限（CKA 认知考点）。
Secret 的四种类型
类型用途键要求
Opaque（默认）通用敏感值：密码 / Token / API Key任意键
kubernetes.io/tlsTLS 证书（Ingress 的 HTTPS）固定 tls.crt + tls.key
kubernetes.io/dockerconfigjson私有镜像仓库凭据固定 .dockerconfigjson
kubernetes.io/service-account-tokenSA 令牌（系统使用）自动管理
两个“非通用”消费特例（不经 env / 卷，被系统直接引用）：
tls 类型 → Ingress 的 spec.tls.secretName（实验 07 Ingress TLS）
dockerconfigjson 类型 → Pod 的 imagePullSecrets（拉私有镜像时用它认证）
kubectl create secret tls my-tls --cert=cert.crt --key=key.key
kubectl create secret docker-registry regcred --docker-server=HOST --docker-username=USER --docker-password=PASS
Secret 的安全边界
消费方式与 ConfigMap 完全相同（卷 / env + 两个系统级特例）——区别只在数据敏感性：Secret 更“金贵”，只给需要的 Pod 挂
RBAC 收紧
get secret 就是拿到全部值——Secret 的读权限要单独授权（第 11 章授权机制）
etcd 静态加密
默认 etcd 里 Secret 是明文存储——配 EncryptionConfiguration 落盘加密，防备份泄露（实验 09 Lab 9）
最小权限
一个 Secret 只给需要的命名空间 / 应用；不用的不创建、不授权；定期轮换
外部密钥管理（进阶）
生产可接 External Secrets（Vault / AWS Secrets Manager），集群里不落明文——知道存在即可
一句话：把 base64 当加密是新手最常见的误解——Secret 的安全永远靠“权限 + 加密存储”，而不是编码本身。

Downward API：注入“自己是谁”
第 4 章 §4.5.4 已讲过 Downward API（实验 06 补充实操）——本章对比，建立“三种注入”的完整图景
注入来源对象典型内容使用
ConfigMap外部配置数据库地址、开关、配置文件应用“要什么”
Secret外部敏感配置密码、Token、证书应用“凭什么”
Downward APIPod 自身元数据Pod 名、命名空间、节点名、labels应用“我是谁”
应用容器（env / 卷 两种注入通道）：ConfigMap → 外部配置（8.2） · Secret → 敏感配置（8.3） · Downward API → 自身元数据（§4.5.4）
判断标准：数据是“环境给的”（CM / Secret）还是“我自己身上的”（Downward）？
注入字段：fieldRef env（Pod 名 / 命名空间 / 节点名）+ downwardAPI 卷（labels / annotations 写进文件）
配置管理最佳实践 · 实验演练指引
最佳实践（生产）
01
配置全进对象：Deployment yaml 零硬编码（地址 / 密码 / 开关不出现）
02
按敏感性分流：非敏感 → ConfigMap；敏感 → Secret（别全放 CM）
03
文件名即配置：配置文件用卷挂载（热更新）；少量参数用 env
04
Secret 最小权限：RBAC 收紧 + etcd 加密 + 定期轮换
05
多环境复用：同一镜像 + 不同命名空间的 CM/Secret = 一套镜像跑 dev/prod
06
修改流程：改 CM（卷方式）→ 自动热更新；改 env → 滚动重启 Pod
