10.1
存储问题全景
▸ 容器文件系统为什么“靠不住”：可写层随 Pod 一起消失
▸ 三个存储需求：持久化 / 共享 / 解耦
▸ K8s 的答案：卷 → PV/PVC → StorageClass 层层抽象
存储问题全景
容器文件系统为什么“靠不住”：写入发生在镜像可写层——容器删除，可写层一起消失
Pod 重建 → 容器内文件全部丢失　｜　Pod 被调度到其他节点 → 原节点上的数据够不着
01
持久化
数据跨 Pod 生命周期存活——删了重建，数据还在
02
共享
Pod 内多个容器共享数据（sidecar 读主容器日志）
03
解耦
应用不关心底层细节（本地盘/网络盘/云盘一样用）
承接第 4 章 Pod“无状态”认知：需要持久数据的应用（数据库 / 上传文件）必须显式挂存储
K8s 的答案：层层抽象——卷（Pod 级）→ PV/PVC（集群级）→ StorageClass（自动化）
10.2
卷（Volume）：Pod 内的存储抽象
▸ emptyDir：Pod 内临时共享盘——Pod 删除即清空
▸ hostPath：宿主机目录——数据在节点磁盘，绑定节点
▸ configMap / secret：只读配置卷（第 8 章配置注入）
▸ 边界认知：卷都“绑定节点”——单机思维，跨节点要靠集群级抽象
卷（Volume）：Pod 内的存储抽象
卷是 Pod 级概念：声明在 Pod 里、挂载进容器，生命周期与 Pod 一致
emptyDir · 临时共享盘
创建时为空目录：容器重启不丢，Pod 删除即清空
典型用途：容器间共享（sidecar 读主容器日志）、临时缓存
Pod 被调度到别的节点 = 新 Pod = 新 emptyDir（数据不迁移）
（实验 08 Lab 1：emptyDir 随 Pod 消失）
hostPath · 宿主机目录
直接挂宿主机的一个目录（如 /data/mysql）
数据在节点磁盘上——Pod 删了还在，但只在该节点
Pod 漂移到其他节点就找不到数据
典型用途：单节点实验、kubelet 等系统组件（实验 08 Lab 2）
configMap / secret · 配置卷
第 8 章的配置注入：键变文件
本质也是卷——只读配置卷
用途：配置与密钥以文件形式挂进容器
边界认知：emptyDir 和 hostPath 都“绑定节点”——它们是“单机思维”的存储
多节点集群要“数据跟着应用走”→ 需要集群级抽象（PV/PVC）
10.3
PV 与 PVC：存储解耦（核心）
▸ 为什么需要两层：应用不写存储细节、管理员统一管理资源
▸ PV：集群级资源——管理员“提供什么”（容量/访问模式/回收策略）
▸ PVC：命名空间级请求——应用“需要什么”（只写 PVC 不写底层）
▸ 生命周期：Provision → Bind → Use → Reclaim
▸ CKA 核心考点：绑定机制、访问模式、回收策略、静态 vs 动态
为什么需要两层 · PV：存储的“货架”
直接让应用指定宿主机目录（hostPath）的问题：① yaml 里写死了存储细节（路径/机器）——换存储就要改应用　② 管理员想统一管理存储资源（哪些盘可用/多大/怎么回收）没有抓手
解耦设计（与 RBAC 的 Subject/Binding 思想同源）：PV——管理员“提供什么”；PVC——应用“需要什么”，应用不知道也不关心底层是 NFS 还是云盘
PV —— 集群级资源
一块“已就绪的存储”
由管理员创建（或 StorageClass 自动创建）
描述：容量 · 访问模式 · 回收策略 · 底层实现
底层实现：hostPath / NFS / 云盘（CSI）
apiVersion: v1
kind: PersistentVolume
metadata:
name: mysqldata-pv
spec:
capacity:
storage: 5Gi
accessModes:
- ReadWriteOnce
persistentVolumeReclaimPolicy: Retain
hostPath:
path: /data/mysql
访问模式 · 回收策略
访问模式（Access Modes）：一块 PV 能被几个节点/几个 Pod 同时用
回收策略（Reclaim Policy）：PVC 删除后，PV 怎么处理
访问模式含义
ReadWriteOnce（RWO）单节点读写（数据库标配）
ReadOnlyMany（ROX）多节点只读
ReadWriteMany（RWX）多节点读写（共享存储如 NFS 才支持）
策略行为
Retain保留数据（PV 变 Released，管理员手动处理——数据安全）
Delete自动删除底层存储（云盘等可自动删）
Recycle（已废弃）清理后复用
核心认知：访问模式是“底层存储能力”的约束——hostPath 只能 RWO；NFS 支持 RWX。应用声明 PVC 时选的模式必须 PV 支持。
（实验 08 Lab 3：静态绑定验证访问模式与容量匹配）
PVC：应用的存储请求
PVC = 命名空间级请求：应用声明“需要多大、什么访问模式”——只写 PVC，不写底层细节
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
name: mysqldata
spec:
accessModes:
- ReadWriteOnce
storageClassName: "" # 禁用动态供应（§10.4）
resources:
requests:
storage: 5Gi
匹配规则（静态绑定）
容量 ≥ 请求 && 访问模式匹配 && storageClassName 匹配
→ 一个 PV 绑定一个 PVC（一对一）
管理视角：PV = 我提供什么
应用视角：PVC = 我需要什么
⚠ 实测易错点：有默认 StorageClass 时，PVC 不写 storageClassName 会走动态供应——静态绑定必须写 ""（实验 08 Lab 3）
生命周期 · 静态 vs 动态
① Provision 供应
管理员建 PV / 动态供应自动建
→
② Bind 绑定
PVC 匹配 PV → 状态 Bound
→
③ Use 使用
Pod 挂载 PVC 写数据
→
④ Reclaim 回收
PVC 删除 → 按回收策略处理 PV
PV：Available（待绑定）→ Bound（已绑定）→ Released（PVC 删了，Retain 后）→ Available / 删除
PVC：Pending（等待匹配）→ Bound（匹配成功）→ 删除
排障：PVC 一直 Pending → kubectl describe 看 Events——检查 PV 是否存在 / 容量 / 访问模式 / SC 是否一致
对比静态绑定动态供应
谁建 PV管理员手动建StorageClass 自动建
适用存储资源固定 / 要精细控制大量 PVC、云环境自动扩
成本每个 PV 都要手工声明即用
（实验 08 Lab 3 手动建 PV + PVC 静态绑定；Lab 4 动态供应——亲手对比两种方式）
10.4
StorageClass：动态供应（自动化）
▸ 为什么需要：静态绑定每个应用都要手动建 PV——忙不过来
▸ provisioner 自动创建 PV 并绑定——声明即用
▸ 默认类：PVC 不写 storageClassName 时自动用它
▸ 绑定模式 WaitForFirstConsumer：节点本地存储的必需
▸ 在线扩容 + 快照：磁盘管理与数据保护手段
StorageClass：让“建 PV”自动化
静态绑定的问题：每个应用都要管理员先手动建好 PV——应用多了根本忙不过来；且 PV 容量是死的（应用要 8G 但只建了 5G 的 PV？）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
name: local-path
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
机制：声明即用
PVC（storageClassName: local-path）
→ provisioner 收到请求 → 自动创建 PV（在节点本地目录建文件夹）
→ 自动绑定 → PVC Bound → Pod 挂载使用
默认 StorageClass：storageclass.kubernetes.io/is-default-class: "true" 注解标记默认类——PVC 不写 storageClassName 时自动用它
教学顺序（本课程设计）：StorageClass 讲完概念再安装——实验 08 Lab 4 才装 local-path；学完 10.3（静态）再学 10.4（动态），对比最清晰
绑定模式 · 回收策略
Immediate · 立即绑定
PVC 创建就绑定（PV 立即建好）
——可能建在与 Pod 无关的节点上
适合网络存储（NFS / 云盘）
WaitForFirstConsumer · 等消费再绑定
等第一个 Pod 调度后再绑定——PV 建在 Pod 所在节点
local-path 这类“节点本地存储”必须用这个：提前绑定可能建在别的节点，Pod 调度过来时数据在别处
回收策略：动态供应的 PV 跟随 StorageClass（reclaimPolicy: Delete 常见）——PVC 删除 = 数据删除（local-path 会删掉本地目录）
要保留数据：临时改 PV 的回收策略为 Retain，或用备份
⚠ PVC 删除 = 数据删除：Delete 策略下 local-path 会删掉本地目录——删 PVC 前确认数据已备份
（实验 08 Lab 4：安装 local-path 后观察“PV 自动生成、目录自动创建”）
在线扩容 · Volume Snapshot
PVC 在线扩容（不重建 Pod）
问题：磁盘满了怎么办？生产刚需
前提：StorageClass 的 allowVolumeExpansion: true（未开启则 PVC 的 storage 不可改）
生效：底层存储支持时应用无感（local-path 支持）；部分存储需 Pod 重启
⚠ 只能扩不能缩——缩减有数据风险，K8s 不支持
kubectl patch pvc mysqldata \
-p '{"spec":{"resources":{"requests":{"storage":"10Gi"}}}}'
VolumeSnapshot · 存储快照（数据保护）
CSI 快照：给 PVC 打“时间点快照”——比拷贝文件更一致、更快
用途：备份前的快速一致快照 / 数据库迁移 / 测试环境克隆
恢复：从快照创建新 PVC（VolumeSnapshotContent）
前提：底层 CSI 驱动支持快照——local-path 不支持；云盘/NFS 类支持
示例：source.persistentVolumeClaimName: mysqldata
与第 14 章 etcd 快照的区别：etcd 快照保“集群状态”、VolumeSnapshot 保“应用数据”——两者互补（Velero 灾备就是组合使用）
10.5
存储方案选型：本地 vs 共享 vs 云盘
▸ local-path：节点本地目录——零成本，但单节点 / 不可共享 / 无冗余
▸ NFS / 云盘：多节点可访问（RWX 共享）
▸ CSI：Kubernetes 与存储厂商的标准接口（生产接入方式）
▸ 选型决策树：持久 → 共享 → 生产 → 核心
▸ 多副本共享的前提是存储可共享
local-path 的本质与局限 · 共享存储
local-path：PV = 节点上的一个本地目录
路径：/opt/local-path-provisioner/<pvc名>
优点：零成本、快（本地盘）、教学演示动态供应足够
局限（必须理解）：
① 单节点：Pod 漂移/扩容到其他节点 → 数据够不着
② 多副本挂同一 PVC（RWX）不支持——local-path 只能 RWO
③ 节点故障 = 数据风险：本地盘没有冗余
（实验 11 WordPress 多副本共享 PVC 受限的根源）
方案特点 · 适用
NFS网络文件系统：一台服务器导出目录，所有节点挂载（支持 RWX）——自建环境多副本共享存储，教学扩展首选
云盘 CSI云盘挂到节点，一般 RWO；对象存储 OSS/S3 天然共享——云环境生产
分布式存储Ceph / Longhorn：软件定义存储，强一致/多副本——大规模生产
水平扩展的前提是存储可共享——这也是 local-path 最本质的局限（实验 11 的教训）
选型要点：要共享 → 必须 RWX 方案（local-path 不行）；要生产 → 必须可托底的方案（云盘 / 分布式）
选型决策树 · CSI 标准接口
应用需要持久存储？
否 → emptyDir / 不挂
是 ↓
多副本要共享？
是 → NFS / 对象存储（RWX）
否 ↓
生产环境？
否 → hostPath / local-path
是 ↓
核心数据库？
是 → 分布式存储 / 云盘 + 备份
否 → 云盘 CSI（RWO）
读图要点：判断顺序——持久与否 → 是否共享 → 是否生产 → 是否核心；“共享”与“生产”是两条最关键的岔路
CSI（Container Storage Interface）：K8s 与存储厂商的标准接口（类似第 3 章 CRI）——任何存储实现 CSI 就能被 K8s 动态供应，“装一个 CSI 驱动”就是接入某类存储
实例：Rook-Ceph——Ceph（分布式存储，多副本/自愈）经 Rook（Operator）部署进集群，以 CSI 驱动提供动态供应（StorageClass）
