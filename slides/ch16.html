16.1
排障方法论：先有框架，再动手
▸ 分层排查框架：从外到内五层，每层专属命令
▸ 证据链思维：现象 → 事件 → 日志 → 指标 → 根因
▸ 排障三条铁律：报错即答案 / 先恢复再排查 / 一次只改一个
分层排查框架：从外到内，逐层定位
01
节点层：机器/kubelet 正常吗？（NotReady？）
systemctl / journalctl / df / free
02
Pod 层：调度/镜像/状态正常吗？（Pending/CrashLoop？）
kubectl get pods -o wide / describe
03
容器层：应用本身正常吗？（日志/退出码）
kubectl logs --previous / exec
04
网络层：流量/名字解析通吗？（Endpoints/DNS）
kubectl get endpoints / nslookup
05
存储层：卷挂载/绑定正常吗？（Pending/FailedMount）
kubectl get pvc / describe
读图要点：先确认“下面一层没白查”——节点挂了，查 Pod 日志是浪费；每层都有专属命令。
证据链思维：现象 → 事件 → 日志 → 根因
取证顺序就是证据链——不要一上来乱敲命令
① 事件
集群视角
kubectl get events -A
kubectl describe xxx
“发生了什么”
Scheduled / Pulled / Unhealthy / Killing…
② 日志
应用视角
kubectl logs <pod>
--previous
“应用说了什么”
报错堆栈 / 连接失败…
③ 指标
资源视角
kubectl top
pod / node
“资源佐证”
内存超限 / OOM…
根因定位 → 修复 → 验证
describe 的 Events 段永远是最快的切入点——90% 的问题在事件 + 日志两步内定位。
排障纪律：三条铁律
01
报错信息就是答案
K8s 的报错几乎都直说“差在哪”：manifest not found=镜像名错、配额、调度条件——先读报错，再想别的
02
先恢复、再排查
生产故障第一优先恢复业务（rollout undo 回滚、scale 副本、重启），恢复后再慢慢查根因
03
一次只改一个
改完验证、不行再改下一个——多变量同时改 = 无法定位（与 Git 二分思路一致）
纪律的本质：把排障变成“可复现的流程”而不是“碰运气”
16.2
各层排障详解
▸ 节点层：NotReady —— kubelet 心跳与节点资源
▸ Pod 层：Pending / ImagePullBackOff / CrashLoopBackOff
▸ 容器层：logs / exec / kubectl debug
▸ 网络层：Endpoints / DNS / 连通性
▸ 存储层：PVC Pending / FailedMount
节点层：NotReady
判断依据：kubectl get nodes 显示 NotReady（Ready 依赖 kubelet 心跳 + 网络就绪）
kubectl get nodes # 哪台 NotReady？
kubectl describe node node2 # 看 Conditions/事件
ssh 到该节点：
systemctl status kubelet # kubelet 活着吗？
journalctl -u kubelet -n 50 # kubelet 日志（第一手线索）
df -h / free -m # 磁盘满/内存不足？（节点资源压力）
ip a # 网络通吗？（CNI 依赖）
常见根因
kubelet 挂了/配置错 · 磁盘满（镜像清理）· 内存压力 · 网络插件（calico）异常 · 证书问题
Pod 层：Pending / ImagePullBackOff / CrashLoopBackOff
判断依据：kubectl get pods -o wide 看 STATUS
状态含义排查路径
Pending未调度/未就绪describe 看 Events：资源/亲和/污点，或镜像拉取中
ImagePullBackOff镜像拉不下来Events：镜像名/标签/私有仓库凭据/网络
CrashLoopBackOff容器反复崩溃logs --previous 崩溃前输出；Last State 退出码
探针失败被重启/被摘除describe 事件：哪个探针、为什么失败
CrashLoop 退出码解读（第 4 章 §4.4.1）——先读退出码，再查日志
0 = 正常退出（任务型用了 Always）
1 = 应用错误（看日志）
127 = 命令不存在（镜像里没有，如 busybox 无 bash）
137 = SIGKILL（OOM/被强杀）→ 查 limits 与 top
143 = SIGTERM（被优雅终止，可能正常下线）
容器层：应用自己
Pod Running 但功能不对 → 进容器看应用（常见坑：环境变量/配置注入错了——describe 核对 Env 与 Mounts，第 8 章）
kubectl logs <pod> --tail=50 # 当前日志
kubectl logs <pod> --previous # 崩溃前的日志
kubectl exec -it <pod> -- sh # 进容器（v1.36 用 --）
kubectl describe pod <pod> # 状态/环境变量/挂载（验证配置对不对）
Pod 里没有 shell/工具（精简镜像）怎么办？——不 SSH 进节点（不干净、权限大），用 kubectl debug：
① 临时容器（v1.23+ 稳定）：kubectl debug -it <pod> --image=nicolaka/netshoot --target=<容器名> -- sh（共享进程/网络命名空间，排障后自动消失）
② 副本调试：kubectl debug <pod> -it --copy-to=debug-pod --image=busybox -- sh（启动调试副本，不改原 Pod）
③ 节点调试：kubectl debug node/<节点名> -it --image=ubuntu（在节点上起特权调试 Pod，替代 SSH）
决策逻辑：能进容器 → exec；容器没工具/进不去 → debug 临时容器；要查节点 → debug node——全程 kubectl，不给 SSH 权限。
网络层：访问不通（Service/DNS 排查流程）
01
Service 有后端吗？
kubectl get endpoints web-svc
ENDPOINTS 为空 = selector 没匹配上（检查 Service 与 Pod 标签）
02
DNS 解析对吗？
kubectl exec xxx -- nslookup web-svc.default.svc
解析失败 = Service 名/命名空间写错，或 coredns 异常
03
连通性：
kubectl exec xxx -- wget -O- http://web-svc
通 = 网络 OK；不通 = kube-proxy/CNI 问题
经典根因：Service 的 selector 拼错标签（app=web vs app=Web）→ Endpoints 空 → 服务 502——实验 10 Lab 4 亲手踩过。
存储层：卷挂不上
kubectl get pvc # PVC 状态（Pending = 没绑定）
kubectl describe pvc # Events：no persistent volumes available（没有匹配的 PV）
kubectl get pv # PV 存在吗/容量/访问模式/SC 匹配吗
kubectl describe pod # Events 的 FailedMount（挂载失败：路径/权限/存储节点）
PVC Pending = PV 不匹配
容量 / 访问模式 / SC 对不上（第 10 章 §10.3.4）
→ 补 PV 或改 SC
FailedMount = 底层存储问题
节点挂了 / 权限问题
→ 修底层存储（不是改 PVC）
判断要点：先分清是“没有匹配的 PV”（PVC Pending）还是“挂不上”（FailedMount）

16.4
可靠性工程：让故障少发生
▸ 发布可靠性：滚动更新策略调优（0/1 零中断）
▸ 下线可靠性：优雅终止深化（preStop + grace period）
▸ 驱逐可靠性：PDB 保护计算（自愿中断）
▸ 主动演练：混沌思想——故障会来，不如主动让它来一次
发布可靠性 + 16.4.2 下线可靠性
发布：滚动更新策略调优
默认 25%/25%：允许短暂少 1 个副本（快速但有小中断）
maxUnavailable: 0
maxSurge: 1
核心服务 0/1：任何时刻不少服务 + 多起一个 → 新 Pod 就绪（readiness）→ 才停旧的 → 零中断发布
下线：优雅终止深化（§4.4.4）
完整流程：摘流量 → preStop → SIGTERM → grace period → SIGKILL
preStop 做反注册/排空（sleep 或调注册中心 API）
grace period 要够：默认 30s，不够调大 terminationGracePeriodSeconds
验证：发布/缩容时观察旧 Pod 是否“优雅退出”（describe 看 Killing 事件时间线）
前提：新 Pod 必须配 readinessProbe——没有探针的滚动更新是“盲更新”；优雅终止的配置是生产标准动作
驱逐可靠性 + 16.4.4 主动演练
驱逐可靠性：PDB 保护
ALLOWED DISRUPTIONS = 可用副本 − minAvailable（第 6 章 §6.5.2）
价值：节点维护/升级（第 14 章）时业务无损的保障
核心服务必配：数据库 / 网关 / 所有多副本应用
边界：只保护自愿中断（drain），节点宕机管不了（那是控制器自愈的事）
主动演练：混沌思想
“故障会来，不如主动让它来一次”——混沌工程思想（Netflix Chaos Monkey 起源）
受控演练：杀一个 Pod → 验证自愈（ReplicaSet 重建）；停一台 worker（drain + 关机）→ 验证业务迁移 + PDB；断一个副本的网络 → 验证 Service 只把流量给就绪 Pod
目的：验证“系统宣称的能力”真的存在——平时演练过，真出事才不慌
本课程实验 10 Lab 5 与实验 02 Lab 9 的删除对比，就是最小的主动演练。
可靠性 = 发布不中断 + 下线不丢请求 + 驱逐有保护——三件套对应“怎么不出事”
SRE 运营规范：把可靠性“制度化”
SLO / Error Budget
SLI（指标）→ SLO（目标）→ SLA（对外承诺）
常见 SLI：可用性（成功/总请求）、延迟（P99）、吞吐
核心交易：可用性 ≥99.95%，P99 < 500ms
内部工具：可用性 ≥99.9%，P99 < 2s
Error Budget：99.95% SLO = 每月允许 21.9 分钟不可用
预算耗尽 → 冻结新功能发布聚焦稳定性；充足 → 可激进发布
故障复盘（Post-mortem）
模板：① 事件概要（何时/多久/影响范围）② 时间线（精确到分钟）③ 根因分析（5 Whys）④ 影响评估 ⑤ 改进措施（每条有 Owner + Deadline）⑥ 经验教训
文化：对事不对人（Blameless）；72 小时内完成初稿；改进项进入排期跟踪
核心认知：复盘的价值不在“追责”而在“系统改进”——每个改进措施闭环，SLO 才会逐年提高（配合第 14 章 §14.6 运维日历执行）。
