18.1
从需求到架构
▸ 需求拆解：一个博客站 → 四个子问题（数据 / 密码 / 前端 / 访问）
▸ 架构核心原则：数据与应用分离
▸ 前端无状态多副本 · 数据库有状态独立存储
需求拆解：一个需求，四个子问题
需求：发布一个 WordPress 博客站——域名访问、可注册发文、数据不能丢、流量大了能扛。
拆成四个子问题，每个都对应前面某章机制。

WordPress Deployment（前端 · 无状态）
多副本 + HPA + 探针——删了重建不影响业务，可随时折腾（扩缩/滚动更新）
数据挂 PVC：wordpress-pvc（上传文件/主题）
MySQL StatefulSet（数据库 · 有状态）
稳定标识 mysql-0 · 有序启动 · 独立 PVC（数据持久、身份稳定）
密码 = Secret mysql-pass（不落 yaml）；经 MySQL Service 服务名连接
读图要点：一条入口、两条数据线——所有流量经 Ingress → Service 分发；前端无状态挂 PVC，数据库有状态独立 PVC + Secret。
决策记忆：“能无状态就无状态，必须有状态就给它最稳妥的家”——分离是容器化架构的第一原则。

扩展层：HPA + 多副本（存储限制的认知）
① scale 到多副本（第 5 章）
kubectl scale deployment wordpress --replicas=5
→ Pod 变 5，多副本分担流量（同一节点可共存）

⚠ local-path 的边界（第 10 章 §10.5.1）
wordpress-pvc 是节点本地存储：多副本跨节点时 PVC 无法同时挂载（RWO + 单节点）→ 教学环境“多副本”堆在同一节点；生产多副本共享存储必须用 NFS / 云盘。
这个限制就是第 10 章选型知识的实战体现：存储选型决定你能怎么扩展。

“能跑”与“生产可用”的差距就在保护层——演练跑通链路后，对照保护层清单逐项补配。
验证体系：怎么证明“能用了”
三个验证对应三层承诺：通不通（全链路）· 丢不丢（持久化）· 够不够（扩展）
① 全链路验证 —— 证明“链路通了”
curl -H "Host: wp.example.com" http://节点IP:NodePort/wp-admin/install.php → 返回 WordPress 安装页
→ 证明：Ingress 路由 ✓ → Service 转发 ✓ → Pod 运行 ✓ → MySQL 连通 ✓；首次访问 302 到安装页，用 -L 跟随（实验 11 实测）
② 持久化验证 —— 证明“数据不丢”
echo persistence-ok > /var/www/html/persist.txt（PVC 里） → 删除全部 WordPress Pod → 新 Pod cat 读取 → persistence-ok
→ 证明：PVC 持久化生效（第 10 章“删 Pod 数据还在”）
③ 扩展验证 —— 证明“能扛流量”
kubectl scale deployment wordpress --replicas=5 → Pod 变 5；kubectl get hpa（CPU 超目标自动扩）
→ 证明：弹性机制就绪（第 5 / 7 章）
清理规范：先入口后数据
清理顺序的原则：先停流量 → 再删应用 → 最后删数据（第 10 章“PVC 删除 = 数据删除”）
① 入口
删 Ingress
删 HPA（先停流量与伸缩）
→
② 应用
删 Deployment
删 Service（工作负载消失）
→
③ 数据
删 PVC
确认数据不要了才删！
→
④ 凭据
删 Secret
最后删命名空间（清残留）
删除顺序的意义：流量与伸缩先停，避免删除过程中仍有请求进来；工作负载消失后再动数据，避免重建读取失败。
PVC 删除 = 数据物理删除（local-path Delete 回收）——确认不要数据再删；想保留就留着 PVC。
展望：CRD 与 Operator（集群扩展机制）
前 17 章用的是 Kubernetes 内置资源（Pod / Deployment / Service…）；生产中还常见“会自我管理”的扩展资源（cert-manager 自动签发证书、Prometheus Operator 管理监控）——它们的底座就是 CRD + Operator。
CRD：自定义资源定义
让 Kubernetes 认识“你自己的资源类型”——业务对象成为一等公民
kind: Certificate → apply 创建 → kubectl get certificates 查看
注意：CRD 只是“数据表”——对象创建了，谁来处理它？
Operator：CRD + 控制器
“会处理自定义资源的控制器”（第 5 章控制循环模式复用）
cert-manager：声明 Certificate → 自动申请/校验/签发 → 写入 tls Secret → 到期续期
（第 9 章 Ingress TLS 的证书从此“自动化”）
Operator管理什么
cert-manager证书自动签发与续期
Prometheus OperatorPrometheus / Grafana 实例的生命周期
云厂商 Operator云资源（数据库 / 负载均衡）即代码
数据库 OperatorMySQL / PostgreSQL 集群（主从 / 备份）
决策逻辑：资源是“标准 K8s 对象”→ 用 Helm 装（第 17 章）；需要“应用自身运维逻辑”→ 找/写 Operator（CRD + 控制器）——Helm 解决“怎么装”，Operator 解决“装完怎么自我管理”。
